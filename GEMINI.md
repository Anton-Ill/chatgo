# Chatgo Project Rules and Workflows

## Стек технологий и стандарты кодирования
- **Язык**: PHP 8.x.
- **Стандарт кодирования**: PSR-12.
- **База данных**: MySQL (использовать исключительно PDO через `DB::getConnection()` из [db.php](file:///e:/01_Chatgo/config/db.php)).
- **Качество кода**: Запрещено оставлять TODO-комментарии и незавершенный код.
- **Интерфейс**: Сервис разрабатывается с акцентом (упором) на удобство использования на мобильных устройствах (mobile-first).


## Структура базы данных (`chatgo`)
- `users`: Пользователи системы.
- `auth_tokens`: Токены беспарольного входа (Magic Link).
- `channels`: Каналы связи (`telegram`, `whatsapp`, `vk`, `instagram`, `max`).
- `chats`: Чаты с клиентами, привязанные к каналам (`client_external_id`).
- `messages`: Входящие и исходящие сообщения.

## Рабочие процессы (Workflows)
1. **Проверка синтаксиса**: После каждого изменения PHP-файлов запускать `php -l path/to/file.php`.
2. **Маршрутизация сообщений**:
   - Входящие сообщения от клиентов регистрируются в `chats` и `messages` со статусом `incoming`.
   - Ответы оператора отправляются через внешние API платформ и сохраняются как `outgoing`.
3. **Безопасность**: Запросы к прокси-шлюзу Telegram проверяются по токену и ключу `CHATGO_SECRET`.

## Правила разработки и безопасности
1. **Безопасность файлов**: Запрещено удалять любые файлы проекта без явного согласия пользователя, за исключением временных диагностических файлов.
2. **Диагностика и тесты**: Все ручные диагностические и тестовые скрипты должны находиться строго в папке `tests/manual/` и именоваться по шаблону `test-<название>.php`. Все временные отладочные вставки (логи, метки `[DEBUG]`) должны быть удалены после отладки.
3. **Согласование и обсуждение**: Запрещено вносить изменения в код без согласования. Перед предложением решения необходимо кратко объяснить суть проблемы, предложить варианты с плюсами (+) и минусами (-), указать рекомендуемый вариант и дождаться согласия.
4. **Разделение ролей**:
   - **Архитектор**: только проектирует, составляет план изменений и формулирует открытые вопросы. Изменять рабочий код запрещено.
   - **Разработчик**: переходит к реализации и написанию кода только после одобрения плана пользователем и ответа на открытые вопросы.
